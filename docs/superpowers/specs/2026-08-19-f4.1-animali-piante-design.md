# F4.1 — Animali e piante (motore + catalogo completo)

Data: 2026-08-19
Stato: approvato in brainstorming, da eseguire
Progetto: web app di coppia "Fabrizio & Emily"

---

## 1. Contesto e scope

Ultima fase del piano originale (F5 → F6 → F2 → F3 → F4), dopo F3 (Tris,
Forza 4, Trivia) completa e in produzione. Come F3 è stata spezzata in
sotto-progetti per gioco, F4 si spezza in due:

- **F4.1** (questa spec): il motore di cura completo — sblocco, statistiche
  che decadono nel tempo, azioni di cura, integrazione in Home — **con già
  dentro l'intero catalogo di 32 animali + 15 piante**. Il catalogo è dato
  statico frontend, come le domande di Trivia: popolarlo per intero costa
  poco e non giustifica una fase a sé.
- **F4.2** (non ancora progettata): skin/colori acquistabili separatamente
  per ogni animale. Rimandata di proposito — riuserà `item_prices` /
  `owned_items` / `purchase_item` di F6 esattamente come le skin erano già
  state anticipate in quella spec.

Dal README originale: sistema di cura con animali/piante che hanno
statistiche (fame, pulizia, gioco/affetto per gli animali; acqua/luce per le
piante) che decadono nel tempo e vanno reintegrate con azioni, sbloccabili a
monete, con tassi di decadimento e bisogni diversi per specie.

## 2. Decisioni prese, con le motivazioni

| Decisione | Scelta | Perché |
|---|---|---|
| Suddivisione | **F4.1 (motore + catalogo completo) / F4.2 (skin, dopo)** | Stesso principio di F3: separare per rischio/dimensione, non per contenuto — il catalogo è dato statico a basso rischio, le skin sono un sistema di personalizzazione a parte. |
| Ordine di sblocco | **Libera scelta fra tutte le 47 specie** | Stesso principio dei temi di Shop: l'intero catalogo è visibile da subito (bloccato finché non si compra), nessuna progressione forzata. |
| Trascuratezza prolungata | **Nessuna conseguenza permanente** | Le statistiche restano a zero e l'animale/pianta resta segnalato come bisognoso finché non si interviene — coerente col tono positivo dell'app, sempre recuperabile, mai "perso". |
| Nome personalizzato | **Testo libero, modificabile in ogni momento** | Non solo alla prima adozione: la coppia può rinominare quando vuole, nessuna lista predefinita. |
| Velocità di decadimento | **Un ciclo pieno→vuoto sull'ordine di un giorno, variabile per specie e per statistica** | Pensato per una routine quotidiana di controllo. Il README chiede esplicitamente tassi diversi anche fra le statistiche della STESSA specie (es. koala: fame lenta; cane: gioco/affetto veloce; pony: fame veloce) — non solo fra specie diverse. |
| Layout della schermata | **Due sotto-sezioni: Animali / Piante** | Rispecchia la distinzione del README fra i due tipi di cura, invece di una lista unica mista. |
| Immagini delle specie | **Illustrazioni fornite dall'utente in `public/pets/<species_key>.png`, con fallback automatico a emoji se il file manca** | Non c'è generazione di immagini disponibile in questo ambiente. Il fallback per-file evita di bloccare lo sviluppo/deploy sull'arrivo degli asset: l'app funziona da subito con le emoji, ogni file caricato con il nome giusto sostituisce l'emoji senza toccare codice. |

## 3. Schema dati

Riuso senza modifiche: `item_prices` (una riga per specie, stesso principio
dei temi di F6), `coin_rules` — contiene già `pet_care_action` (2 monete,
cap 30/giorno a persona) e `plant_watered` (3 monete, cap 15/giorno a
persona), seminati fin da F0+F1 in previsione di questa fase.
`spend_coins`/`grant_coins` riusati senza modifiche.

Nuovo:

```sql
create type pet_kind as enum ('animal', 'plant');

-- Una riga per specie SBLOCCATA, condivisa dalla coppia (come couple_state).
-- L'esistenza della riga stessa è il segnale di possesso — niente
-- owned_items per gli animali: a differenza dei temi di F6, qui serve uno
-- stato vivo (statistiche, nome), non solo un flag di possesso.
create table pets (
  species_key text primary key references item_prices(key),
  kind         pet_kind not null,
  nickname     text null,
  stats        jsonb not null,
  -- animali: {"hunger":100,"cleanliness":100,"affection":100}
  -- piante:  {"water":100,"light":100}
  -- Forma decisa dal client: il server non conosce i nomi delle statistiche,
  -- stesso principio di game_matches.state in F2.
  updated_at   timestamptz not null default now(),
  -- Ultima scrittura di stats. Il client proietta il decadimento in avanti
  -- da qui usando i tassi per specie del catalogo frontend — nessun cron,
  -- nessun tick lato server.
  unlocked_at  timestamptz not null default now()
);

grant select on pets to authenticated;
grant select, insert, update, delete on pets to service_role;
alter table pets enable row level security;
create policy read_for_authenticated on pets for select to authenticated using (true);
alter publication supabase_realtime add table pets;
```

Il **costo** di ogni specie vive in `item_prices` (letto da `spend_coins`).
Nome, emoji, curiosità e tassi di decadimento vivono nel catalogo statico
frontend (`features/pets/species.ts`), come le domande di Trivia.

## 4. Funzioni

Nessuna modifica alle funzioni esistenti. Tre funzioni nuove, tutte
`security definer`, tutte nate con zero privilegi (grant esplicito come da
convenzione del progetto):

**`unlock_pet(p_actor person, p_species_key text, p_kind pet_kind, p_initial_stats jsonb) returns pets`**
- `perform spend_coins(p_actor, p_species_key)` — riusa il primitivo
  esistente: lock su `couple_state`, controllo saldo, `insufficient_funds`
  già tradotto in `lib/rpc.ts`, zero nuovo codice per il pagamento.
- `insert into pets (species_key, kind, stats) values (...)`. La violazione
  della chiave primaria (doppio sblocco quasi simultaneo) diventa
  `already_unlocked`, stesso pattern di `already_owned` in `purchase_item`.
- Le statistiche iniziali le decide il client (`p_initial_stats`): il server
  non conosce la forma delle statistiche per specie.

**`care_for_pet(p_actor person, p_species_key text, p_stats jsonb) returns pets`**
- Verifica che la specie sia posseduta: se no, `pet_not_found`.
- Aggiorna `stats = p_stats`, `updated_at = now()`.
- Deriva la reason delle monete **dal campo `kind` già in tabella**, non da
  un parametro del client: `animal → 'pet_care_action'`, `plant →
  'plant_watered'`. Il client non sceglie mai la reason.
- `perform grant_coins(p_actor, v_reason)` — il cap giornaliero già seminato
  (30/15) si applica da solo, nessuna nuova regola economica.
- **Decisione esplicita, non una svista**: il server non ricalcola il
  decadimento né clampa i valori in `p_stats` — si fida del client, stesso
  principio di fiducia già documentato per la risposta corretta di Trivia e
  per l'esito dei giochi. I due giocatori sono la stessa coppia, non
  avversari: non serve una barriera anti-imbroglio fra loro.

**`rename_pet(p_species_key text, p_name text) returns pets`**
- Verifica che la specie sia posseduta (`pet_not_found` se no).
- Valida che il nome, dopo `trim`, non sia vuoto e non superi 40 caratteri
  (`invalid_pet_name` se non rispettato).
- Nessun tracciamento per persona: nome condiviso, modificabile da entrambi
  in ogni momento.
- Aggiorna `nickname` e ritorna la riga.

## 5. Frontend

```
features/pets/
  species.ts          catalogo statico delle 47 specie: key, kind, name, emoji,
                       curiosityFact, costo, moltiplicatori di decadimento per statistica
  care.ts              logica pura, senza React: proietta il decadimento corrente da
                       stats+updated_at, applica un'azione di cura (clamp 0-100),
                       decide se una specie ha bisogno di attenzioni
  usePets.ts            hook realtime (mirror di useShop): osserva la tabella pets,
                       restituisce { owned: Pet[] } uniti col catalogo per species_key
  SpeciesImage.tsx       <img> verso /pets/<key>.png con fallback automatico a emoji
                       on error — usato ovunque si mostri una specie
  PetCard.tsx             card di una specie nella lista: bloccata (costo + "Unlock")
                       o sbloccata (nome, barre statistiche live-decadenti)
  PetDetail.tsx            vista dettaglio: curiosità, rinomina, barre complete,
                       pulsanti di cura
  pets.module.css

app/pets/page.tsx            sostituisce l'attuale EmptyState: due sotto-sezioni
                            Animali / Piante, ciascuna con le sue card
app/pets/[species]/page.tsx    dettaglio di una specie (rotta dinamica, come /letters/[id])
```

**Home** (`app/page.tsx`): lo slot placeholder "Your animals... Coming
soon" (già impaginato per questa fase, come da commento nel codice) viene
sostituito da una card che elenca le specie possedute con almeno una
statistica sotto soglia (30), con link a `/pets`. Nessuna specie bisognosa
→ messaggio positivo invece della lista vuota.

**Decadimento live**: le barre statistiche si aggiornano nel browser con un
intervallo che ricalcola dal valore salvato + tempo trascorso, stesso
pattern del countdown di Trivia — nessun polling continuo, solo un timer
client-side che ridisegna.

**Azioni di cura**: un bottone per statistica (Feed/Clean/Play per gli
animali, Water/Light per le piante), ciascuno alza la statistica
corrispondente di 40 punti (clamp a 100) e chiama `care_for_pet` con lo
stato risultante. Nessun cooldown lato UI: il limite reale è il cap
giornaliero delle monete già in `coin_rules`, agire oltre il cap resta
possibile ma non paga più (stesso comportamento silenzioso di `grant_coins`
già in uso per lettere/domande/giochi).

## 6. Contenuto: il catalogo delle specie

**32 animali** (3 statistiche: hunger, cleanliness, affection), per
categoria:

| Categoria | Specie (species_key) | Costo |
|---|---|---|
| Domestico (8) | pet_dog, pet_cat, pet_rabbit, pet_hamster, pet_guinea_pig, pet_parrot, pet_goldfish, pet_turtle | 35 |
| Fattoria (6) | pet_pony, pet_goat, pet_sheep, pet_cow, pet_pig, pet_capybara | 35 |
| Esotico (10) | pet_koala, pet_panda, pet_penguin, pet_fox, pet_owl, pet_sloth, pet_otter, pet_hedgehog, pet_chameleon, pet_flamingo | 70 |
| Fantastico (8) | pet_unicorn, pet_dragon, pet_phoenix, pet_griffin, pet_kitsune, pet_kraken, pet_cloud_sprite, pet_moon_rabbit | 140 |

**15 piante** (2 statistiche: water, light), costo uniforme 25: plant_fern,
plant_succulent, plant_cactus, plant_bonsai, plant_orchid,
plant_sunflower, plant_tulip, plant_bamboo, plant_ivy, plant_aloe,
plant_lavender, plant_venus_flytrap, plant_money_tree, plant_peace_lily,
plant_moss_terrarium.

**Tempo base di decadimento pieno→vuoto per categoria** (poi modulato per
statistica, vedi sotto): domestico/fattoria 20h, esotico 30h (specie più
"calme"), fantastico 24h, piante 36h ("cura più semplice" come da README).

**Moltiplicatori per statistica**: il README chiede esplicitamente che
specie della stessa categoria abbiano bisogni diversi fra le proprie
statistiche (es. koala: fame lenta; cane: gioco/affetto veloce; pony: fame
veloce). Il meccanismo: ogni specie ha un moltiplicatore (0.5–1.5) per
ciascuna sua statistica, applicato al tempo base della categoria — es. per
il cane `affection: 1.5` (decade il 50% più in fretta della base) e per il
koala `hunger: 0.5` (decade la metà). La tabella completa dei 47
moltiplicatori (curata a mano per dare personalità a ogni specie, coerente
con l'indole reale/immaginaria dell'animale) viene scritta nel piano di
implementazione, stesso trattamento riservato al testo delle 100 domande di
Trivia nella sua spec — non incide su nomi di specie o file immagine, già
definitivi in questa sezione.

**Immagine**: ogni specie ha un `species_key` che è anche il nome del file
atteso in `public/pets/<species_key>.png` (PNG, sfondo trasparente,
indicativamente 512×512, soggetto centrato). In assenza del file,
`SpeciesImage` mostra l'emoji del catalogo.

**Curiosità**: ogni specie ha un breve testo informativo (1-2 frasi) mostrato
nel dettaglio — scritto durante l'implementazione insieme al resto del
catalogo statico.

## 7. Errori e casi limite

Nuovi codici, da tradurre in `lib/rpc.ts` insieme a quelli già esistenti
(`insufficient_funds`, `unknown_item` sono già tradotti e riusati senza
modifiche da `unlock_pet`):

- `already_unlocked` — sblocco duplicato quasi simultaneo della stessa
  specie (vincolo di unicità sulla chiave primaria).
- `pet_not_found` — azione di cura o rinomina su una specie non ancora
  sbloccata (dato normalmente impossibile dall'interfaccia, ma la funzione
  lo valida comunque, come already fatto altrove nel progetto).
- `invalid_pet_name` — nome vuoto (dopo trim) o oltre 40 caratteri.

Se il decadimento proiettato scende sotto zero (tempo trascorso molto
lungo, es. settimane), il client clampa a zero nella UI — mai un numero
negativo mostrato o inviato al server.

  `rename_pet` (nome valido, nome vuoto, nome troppo lungo).

## 9. Fuori scope in questa fase

Skin/colori acquistabili per gli animali (F4.2, da progettare a parte).
Notifiche push quando una specie ha bisogno di attenzioni (l'unico segnale
è la card in Home, coerente con l'assenza di notifiche push nel resto del
progetto). Un tick server-side/cron per il decadimento — resta calcolato
lato client, come deciso in questa spec.

## 10. Criteri di accettazione

1. Aprendo la schermata Animali e piante, appaiono due sotto-sezioni con
   tutte le 47 specie: bloccate (costo + pulsante) o sbloccate.
2. Sbloccare una specie scala le monete del costo esatto e la fa apparire
   subito, in tempo reale, sull'altro dispositivo.
3. Le statistiche di una specie sbloccata calano visibilmente nel tempo,
   a velocità diverse per statistica e per specie secondo il catalogo.
4. Le azioni di cura alzano la statistica corrispondente e assegnano
   monete, entro il cap giornaliero già esistente in `coin_rules`.
5. Una specie può essere rinominata in ogni momento, il nome è condiviso e
   visibile a entrambi in tempo reale.
6. Nessuna specie trascurata viene mai persa o penalizzata in modo
   permanente.
7. La Home mostra le specie bisognose di attenzioni (statistica sotto 30),
   o un messaggio positivo se non ce ne sono.
8. Le immagini mancanti mostrano l'emoji corrispondente senza errori in
   console e senza rompere il layout.
